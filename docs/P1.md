## 3\. (P1.2) Kontrak API klien

**Endpoint yang dipakai**

|Endpoint|Fungsi|
|-|-|
|`GET /v1/stations?limit=\&offset=`|Daftar stasiun|
|`GET /v1/flaky`|Uji ketahanan: 30% menjawab 503, sisanya lambat acak 0,05-0,4 detik|

**Paginasi:** berbasis offset. `limit` dibatasi server pada 1-500 (bawaan 50), `offset` bawaan 0. Respons berisi `items` dan `next\_offset`. Klien memuat halaman berikutnya dengan `offset=next\_offset` dan berhenti saat `next\_offset` bernilai `null`.

**ETag:** server mengirim header `ETag` (hash isi halaman) dan `Cache-Control: max-age=60`. Klien menyimpan ETag per halaman dan mengirimnya lewat `If-None-Match`; jawaban 304 berarti klien memakai data yang tersimpan. OkHttp tidak melakukan ini otomatis tanpa `Cache`, dan `buildClient` belum mengaturnya, sehingga header perlu ditambahkan manual atau cache diaktifkan.

**Status code dan reaksi aplikasi**

|Status / kondisi|Reaksi aplikasi|
|-|-|
|200|Tampilkan data, simpan ETag|
|304|Tampilkan data dari cache lokal|
|400 / 422|Tampilkan pesan, jangan retry (kesalahan klien)|
|401|Login ulang tanpa menghapus data (relevan setelah Praktik 4a)|
|403 / 404|Tampilkan pesan, jangan retry|
|429|Retry dengan backoff (hormati `Retry-After` bila ada)|
|500|Tampilkan pesan error server, tidak di-retry otomatis oleh interceptor|
|502 / 503 / 504|Retry maksimal 3 kali dengan backoff eksponensial + jitter, lalu tampilkan pesan|
|Timeout / `IOException`|Retry (hanya GET), lalu tampilkan pesan periksa koneksi|

## 4\. (P1.3) Bukti implementasi

**Potongan kode** (`RetryInterceptor.kt` dan `buildClient`, dari Modul P1 Langkah 4):

```kotlin
class RetryInterceptor(private val maxRetries: Int = 3) : Interceptor {
    private val retryable = setOf(429, 502, 503, 504)
    override fun intercept(chain: Interceptor.Chain): Response {
        val request = chain.request()
        if (request.method !in setOf("GET", "PUT", "DELETE")) return chain.proceed(request)
        var attempt = 0
        while (true) {
            try {
                val response = chain.proceed(request)
                if (response.code !in retryable || attempt >= maxRetries) return response
                response.close()
            } catch (e: IOException) {
                if (attempt >= maxRetries) throw e
            }
            val backoffMs = (500L shl attempt) + Random.nextLong(0, 250)  // 0,5 s, 1 s, 2 s + jitter
            Thread.sleep(backoffMs)
            attempt++
        }
    }
}

fun buildClient(withRetry: Boolean): OkHttpClient {
    val b = OkHttpClient.Builder()
        .connectTimeout(5, TimeUnit.SECONDS)
        .readTimeout(10, TimeUnit.SECONDS)
    if (withRetry) b.addInterceptor(RetryInterceptor())
    return b.build()
}
```

Penjelasan hasil:

* Tanpa retry, tingkat sukses 61,7% (37 dari 60), mendekati perkiraan 70% dari server yang menjawab 503 pada 30% permintaan. Dengan retry naik menjadi 96,7% (58 dari 60), mendekati nilai teoretis 1 - 0,3⁴ = 99,2%.
* Panggilan yang di-retry lebih lama karena jeda backoff 0,5 s, 1 s, dan 2 s ditambah jitter 0-250 ms. Satu kali retry menghasilkan sekitar 0,8-1,2 detik (contoh: 1012 ms, 1118 ms, 1004 ms, 821 ms pada profil full). Tiga kali retry menghasilkan sekitar 3,5-4,3 detik (contoh: 4262 ms pada profil full yang akhirnya sukses; 4112 ms pada hsdpa dan 3978 ms pada edge yang tetap gagal setelah 4 percobaan).
* Peluang gagal setelah 4 percobaan adalah 0,3⁴ ≈ 0,8% per panggilan, sehingga 2 kegagalan dari 60 panggilan masih wajar.
* Panggilan pertama pada tiap uji sekitar 520 ms karena membuka koneksi dan inisialisasi awal.

Alasan POST tidak di-retry otomatis: POST tidak idempotent. Bila respons hilang padahal server sudah memproses request, retry dapat membuat data ganda (misalnya pengukuran tersimpan dua kali). Interceptor karena itu hanya me-retry GET, PUT, dan DELETE. POST baru aman di-retry bila ada kunci idempotensi, seperti ID dari klien pada protokol sinkronisasi di Praktik 3.

## 5\. Refleksi

Apa yang terjadi bila 1.000 klien me-retry tanpa jitter pada saat yang sama?

Semua klien yang gagal menunggu waktu backoff yang sama (0,5 s, 1 s, 2 s), sehingga request datang serentak dalam gelombang (thundering herd). Server yang sedang kewalahan menerima lonjakan beban tepat saat mencoba pulih, sehingga kegagalan berulang dan dapat memburuk. Jitter menyebarkan retry sepanjang rentang waktu sehingga puncak bebannya lebih landai.
